## 한 줄 정의

어떤 사용자가 시스템으로 **무엇을 하고 싶은지**를 사용자 입장에서 적은 요구사항.

## 비유

손님이 주방에 넘기는 **주문 쪽지**. "레시피"가 아니라 "매운 거 못 먹는 아이가 먹을 볶음밥"처럼 누가 왜 원하는지가 적혀 있어 요리사가 알아서 맞춘다.

## 예시

사용자 스토리는 "~로서, ~하고 싶다. ~하기 위해서다" 세 조각으로 한 줄.

```markdown
- 3학년 학부생으로서, 모르는 용어를 검색하면 한 줄 정의를 바로 보고 싶다.
  세미나 중에 흐름을 놓치지 않기 위해서다.
  - 완료 조건: 검색창에 "ssh" 입력 후 1초 안에 카드가 뜬다
- 연구실 신입으로서, 카드에 별표를 달아 두고 싶다.
  다음 세미나 전에 다시 볼 용어를 모아두기 위해서다.
```

같은 기능을 유스케이스로 쓰면 행위자와 흐름이 붙어 조금 길어진다.

```text
유스케이스: 카드 검색
  행위자    : 학부생
  기본 흐름 : 검색어 입력 → 제목·별칭이 맞는 카드 목록 → 카드 선택 → 상세 화면
  예외 흐름 : 결과 0건 → "_inbox.md 에 추가할까요?" 안내
```

## 헷갈리기 쉬운 것

- **유스케이스**는 행위자·기본 흐름·예외 흐름을 갖춘 시나리오, **사용자 스토리**는 대화의 출발점이 되는 한 줄 메모. 애자일 팀은 스토리를, 설계 문서는 유스케이스를 선호하는 편.
- **요구사항 명세**는 이런 줄들을 모아 번호 붙여 정리한 문서 전체.
