## 한 줄 정의

현장 전문가가 쓰는 말과 업무 경계를 그대로 **코드의 이름과 모듈 경계**로 삼는 설계법.

## 비유

병원의 **진료과별 장부**. 같은 "환자"라도 원무과에는 수납 대상이고 병동에는 침상 배정 대상이라 부르는 말이 다르니, 억지로 한 장부에 합치지 않고 과마다 장부를 두고 필요한 것만 주고받는다.

## 예시

```text
[입원 관리 시스템 — 바운디드 컨텍스트 나누기]
원무(Billing)   환자 = 수납 대상      용어: 수납, 미수금, 보험 유형
병동(Ward)      환자 = 입원 환자      용어: 입원, 전동, 퇴원, 침상
검사(Lab)       환자 = 검체의 주인    용어: 오더, 검체, 결과 보고

→ 셋이 Patient 클래스 하나를 공유하지 않는다. 컨텍스트마다 Patient 가 따로 있고,
  병동에서 원무로는 "퇴원됨(mrn, 날짜)" 이벤트 하나만 넘어간다.
```

```python
# 유비쿼터스 언어: 간호사가 "전동" 이라 부르면 코드도 회의도 문서도 같은 말을 쓴다
class Admission:
    def transfer_ward(self, to_ward: str, at: datetime) -> None: ...
    # 리뷰에서 "update_ward_id" 같은 이름은 거부 — 현장에 없는 말이다
```

핵심은 둘이다. **유비쿼터스 언어**: 코드·회의·요구사항 문서가 같은 단어를 쓴다. **바운디드 컨텍스트**: 같은 단어의 뜻이 바뀌는 지점이 곧 모듈(또는 서비스) 경계다. 엔티티·값 객체·애그리거트·리포지토리 같은 전술 패턴은 그다음 이야기인데, 거기서부터 외우기 시작하면 대개 실패한다. 트레이드오프: **3명 연구실에서 CRUD 와 분석 대시보드를 만든다면 과하다** — 현장 전문가와 오래 대화할 일도, 뜻이 갈리는 "환자"도 없다. 처방·수가·보험처럼 규칙이 복잡하고 간호사·의사와 몇 달씩 용어를 맞춰야 하는 시스템에서 빛난다.

## 헷갈리기 쉬운 것

- **ERD** 는 테이블 중심, DDD 는 행위·규칙·언어 중심. 같은 patient 테이블이 컨텍스트마다 다른 모델로 보일 수 있다.
- **마이크로서비스**: 바운디드 컨텍스트는 서비스 경계를 긋는 좋은 기준이지만, 컨텍스트 하나가 꼭 서비스 하나는 아니다. 모놀리식 안의 패키지 경계로도 충분하다.
- **클린 아키텍처**는 도메인을 바깥(DB·웹)으로부터 보호하는 구조, DDD 는 그 도메인 안에 무엇을 어떤 이름으로 담을지. 둘은 자주 같이 쓰이지만 따로 써도 된다.
