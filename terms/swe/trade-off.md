## 한 줄 정의

하나를 좋게 하면 **다른 하나가 나빠지는** 관계라서 정답 대신 선택만 있는 것.

## 비유

**노트북 고르기**. 가볍게 만들면 배터리가 작아지고 배터리를 키우면 무거워지니, 둘 다 최고인 제품은 없고 "나는 들고 다니는 사람인가"라는 질문만 남는다.

## 예시

ADR 에 붙이는 비교표 — 오른쪽 두 열이 핵심이다.

```markdown
| 선택지 | 얻는 것 | 내주는 것 | 우리 상황에서는 |
| :-- | :-- | :-- | :-- |
| 환자 ID 인덱스 추가 | 조회가 수십 배 빨라짐 | INSERT 느려짐, 디스크 더 씀 | 조회가 99% — 채택 |
| 통계 결과 Redis 캐시 | DB 부하 감소 | 잠깐 옛 데이터를 보여줄 수 있음 | 처방 화면엔 금지, 통계만 |
| 마이크로서비스 분리 | 팀별 독립 배포 | 운영 복잡도, 네트워크 장애 지점 | 3명 팀 — 기각 |
```

"뭐가 더 좋은 기술인가"가 아니라 **"우리는 뭘 내줄 수 있나"** 로 결정한다. 같은 표라도 팀이 30명이면 세 번째 줄의 답이 뒤집힌다. 흔한 실수는 장점만 나열하는 것과, 모든 축을 다 좋게 만들려다 복잡도만 키우는 것 — 한 축을 **의식적으로 포기**하는 게 설계다. 결정과 이유는 ADR 로 남기고, 면접의 "왜 그 기술을 썼어요?"는 이 표를 말로 풀면 된다.

## 헷갈리기 쉬운 것

- **최적화**는 아무것도 내주지 않고 더 빠르게 만드는 것(같은 결과, 적은 자원). 그런 공짜 개선은 금방 바닥나고, 그다음부터는 전부 트레이드오프다.
- **CAP 이론**은 분산 DB 에 한정된 유명한 트레이드오프 하나. 트레이드오프는 그보다 넓은 사고방식이다.
- **기술 부채**는 "지금 속도를 얻고 나중 수고를 내준다"는 트레이드오프를 택한 결과. 문제는 내주는 게 뭔지 모른 채 택한 부채다.
