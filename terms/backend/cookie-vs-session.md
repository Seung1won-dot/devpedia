## 한 줄 정의

**쿠키는 브라우저에, 세션은 서버에** 사용자 상태를 저장한다는 위치 차이.

## 비유

쿠키는 **내 지갑 속 쪽지**, 세션은 **가게 카운터 뒤 장부**. 쪽지는 내가 고칠 수도 잃어버릴 수도 있지만, 장부는 가게가 관리하고 나는 장부 번호가 적힌 쪽지만 들고 다닌다.

## 예시

| | 쿠키 | 세션 |
|---|---|---|
| 저장 위치 | 브라우저 | 서버(메모리·Redis·DB) |
| 사용자가 볼 수 있나 | 있음(개발자 도구), 고칠 수도 있음 | 없음. 세션 ID 만 본다 |
| 만료 | `Max-Age`/`Expires`, 없으면 브라우저 닫을 때 | 서버가 정한 시간, 또는 로그아웃 |
| 크기 | 쿠키 하나 약 4KB | 서버 자원만큼 |
| 서버 부담 | 없음 | 사용자 수만큼 저장 공간 |

```http
HTTP/1.1 200 OK
Set-Cookie: sid=9f2c1a...; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

둘은 경쟁 관계가 아니라 **세션 ID 를 쿠키에 담아** 같이 쓴다. 서버는 로그인 상태를 세션에 두고 브라우저에는 `sid` 만 주며, 브라우저는 이후 요청마다 그 쿠키를 자동으로 붙인다. 위조되면 안 되는 것(로그인 여부, 권한)은 세션, 위조돼도 그만인 것(다크 모드, 언어)은 쿠키에 둔다. `HttpOnly` 는 JS 가 못 읽게(XSS 대비), `Secure` 는 HTTPS 에서만, `SameSite` 는 다른 사이트에서의 자동 전송을 제한(CSRF 대비)한다. 면접에서는 "쿠키와 세션의 차이는?" 다음에 "세션은 쿠키 없이도 되나?" 가 따라온다 — 된다(URL 이나 헤더에 ID 를 실으면), 다만 쿠키가 자동 전송이라 표준처럼 쓰일 뿐이다.

## 헷갈리기 쉬운 것

- **세션 인증**은 이 둘을 조합한 로그인 방식의 이름. 이 카드는 저장소 개념이고, 로그인 흐름 자체는 `session-auth` 카드에 있다.
- **localStorage** 도 브라우저 저장소지만 요청에 자동으로 붙지 않고 JS 로만 읽으며 5MB 정도로 크다. 자동 전송이 필요하면 쿠키, 아니면 localStorage.
- **JWT** 는 서버가 아무것도 저장하지 않고 토큰 자체에 상태를 넣는 방식. "세션 vs JWT" 는 서버가 기억하느냐 토큰이 기억하느냐의 차이이고, JWT 도 쿠키에 담아 보낼 수 있다.
