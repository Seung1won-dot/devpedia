## 한 줄 정의

그 기술을 고른 이유를 **대안 비교와 우리 상황의 제약**으로 설명하는 것.

## 비유

자취방 계약 이유. "역세권이라서요" 보다 "예산 50만 원 안에서 세 곳 봤는데 A 는 통학 1시간, B 는 곰팡이, 그래서 C" 가 믿음이 간다.

## 예시

```text
Q. "왜 MySQL 대신 PostgreSQL 을 썼나요?"

[나쁜 답]
"요즘 많이 쓰고 성능이 좋다고 들어서요." / "팀원이 써 본 적 있어서요."
  → 검색 결과 요약이거나 남의 선택. 면접관: "그럼 MySQL 은 성능이 나쁜가요?"

[좋은 답 — 대안 → 제약 → 선택 → 결과]
대안 : MySQL, PostgreSQL, MongoDB 를 놓고 봤다.
제약 : 용어 카드에 aliases·tags 같은 배열 필드가 있고, 한글 부분 일치 검색이
       필요했고, 팀 4명 중 SQL 경험자는 2명, 서버 비용은 0원이어야 했다.
선택 : PostgreSQL — 배열·JSONB 컬럼과 GIN 인덱스로 스키마를 안 바꾸고 태그 검색이
       됐고, Supabase 가 Postgres 기반이라 RLS 로 인증까지 한 번에 해결됐다.
결과 : 한글 검색은 pg_trgm 으로 해결했지만 형태소 분석은 못 했다. 다시 한다면
       검색 엔진을 따로 둘지 초기에 판단했을 것이다.
```

정답인 기술은 없다. 면접관이 보는 것은 **선택의 근거 구조**다. "배우고 싶어서" 도 정직한 이유지만, 그렇다면 그렇게 말하고 그 대가(러닝 커브로 일정이 2주 밀림)를 알고 있었다는 걸 보여야 한다. 마지막 "결과/후회" 한 문장이 있어야 선택을 평가할 줄 아는 사람으로 보인다 — 후회를 말하면 감점이라고 생각하지만 반대다. 꼬리 질문은 보통 "그럼 사용자가 10배가 되면 그 선택은 유지되나요?" 인데, 제약이 바뀌면 선택도 바뀐다고 답하면 된다.

프로젝트의 큰 선택(언어·프레임워크·DB·배포 방식·상태 관리)마다 다음을 한 줄씩 채워 두면 면접 답이 그대로 나온다. 프로젝트 중에 ADR 로 적어 두는 게 가장 확실하다 — 6개월 뒤에는 이유가 기억나지 않는다.

| 항목 | 채울 것 | 예 |
| --- | --- | --- |
| 대안 | 최소 2개 | Vite vs Next.js |
| 제약 | 팀·시간·비용·요구사항 중 3개 | SEO 불필요, 정적 호스팅, 4주 |
| 선택 | 한 문장 | SSR 이 필요 없어 Vite |
| 결과·후회 | 한 문장 | 나중에 OG 태그 때문에 SSG 가 아쉬웠다 |

## 헷갈리기 쉬운 것

- **기술 스택 나열**("React, Node, Postgres 썼습니다") 은 목록이지 이유가 아니다.
- **기술 비교 지식**("MySQL 과 PostgreSQL 의 차이는?") 은 일반 CS 질문. 기술 선택 이유는 "그 차이가 우리 프로젝트에서 왜 중요했나" 까지 가야 한다.
- **ADR** 은 그 이유를 프로젝트 안에 남기는 문서 형식. 면접 답변은 ADR 을 1분으로 압축한 것이다.
