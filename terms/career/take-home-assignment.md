## 한 줄 정의

며칠 동안 **실제 기능을 구현해 제출**하고 코드와 설계를 평가받는 전형.

## 비유

요리사 채용에서 칼질 시험(코테) 대신 **"집에서 한 상 차려 오세요"** 하는 것. 맛(동작)만이 아니라 재료 손질(코드 구조)과 레시피 메모(README)까지 본다.

## 예시

```text
과제 안내 예   "게시글 CRUD REST API 를 구현하세요. 로그인은 JWT. 기한 5일. 언어·프레임워크 자유.
              README 에 실행 방법과 설계 의도를 적어 주세요."
제출물        GitHub 저장소 링크(또는 zip) + README
```

평가자가 실제로 보는 순서대로 만든 체크리스트다.

```text
[ ] README 만 보고 1분 안에 실행되나 (docker compose up 또는 npm run dev 한 줄)
[ ] 요구사항을 다 했나, 못 한 것은 "미구현 + 이유" 로 README 에 솔직히 적었나
[ ] 테스트가 있나 — 핵심 로직 단위 테스트 5~10개면 충분, 커버리지 100% 는 안 본다
[ ] 커밋 이력에 과정이 보이나 (init → feat: 글 작성 → feat: JWT 인증 → test: …)
[ ] 왜 이 구조·라이브러리인지 한 문단 (선택 이유 + 버린 대안)
[ ] 예외 처리 — 없는 글 조회, 남의 글 수정, 잘못된 입력에 4xx 를 제대로 주나
[ ] 시크릿(.env, 토큰 서명 키)이 커밋에 안 들어갔나
```

흔한 실수는 정해져 있다. 커밋 하나에 통째로 올리기, 요구하지 않은 기능(관리자 페이지, 소셜 로그인)을 잔뜩 붙이다 기본 기능이 깨지기, README 대로 하면 실행이 안 되기, AI 가 만든 코드를 그대로 넣고 설명 못 하기. 과제 통과 뒤 면접에서 "여기서 왜 이렇게 하셨어요?" 는 거의 확실히 나오고, 그때 답을 못 하면 과제 점수가 무의미해진다. 기한의 70% 에 기본 기능을 끝내고 나머지를 테스트·README·리팩터링에 쓰는 배분이 안전하다.

## 헷갈리기 쉬운 것

- **코딩테스트**는 알고리즘 몇 문제를 몇 시간에. 과제는 실제 기능을 며칠에 — 보는 것도 "정답" 이 아니라 "일하는 방식" 이다.
- **포트폴리오**는 내가 고른 프로젝트. 과제는 회사가 정한 문제를 모든 지원자가 같은 조건으로 푼다.
- **라이브 코딩**은 그 자리에서 실시간. 과제는 집에서 검색·문서를 다 써도 된다.
