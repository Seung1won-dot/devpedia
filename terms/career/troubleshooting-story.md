## 한 줄 정의

막힌 문제를 **증상 → 원인 추적 → 해결 → 배운 것** 네 단계로 정리해 말하는 경험담.

## 비유

병원에서 의사에게 하는 설명과 같다. "어디가 아팠고, 어떻게 원인을 찾았고, 뭘 했더니 나았고, 다음엔 어떻게 예방할지" 네 칸이 다 있어야 진짜 겪은 얘기로 들린다.

## 예시

```text
[나쁜 예]
"Docker 로 배포할 때 에러가 나서 구글링해서 해결했습니다."
  → 증상도 원인도 없다. 면접관이 물어볼 게 없어서 대화가 끝난다.

[좋은 예 — 4단계]
증상   : Caddy 뒤에 올린 React 앱이 첫 진입은 되는데 /terms/os 로 직접 들어가거나
         새로고침하면 404 가 났다.
추적   : 네트워크 탭 → 404 가 Caddy 응답 → 접근 로그를 보니 /terms/os 를 실제 파일로
         찾고 있었다. (처음엔 Vite base 경로를 의심했는데 아니었다)
해결   : Caddyfile 에 try_files {path} /index.html 추가, 전 경로 직접 진입 확인.
배운 것: SPA 는 배포 환경마다 fallback 설정이 필수. 배포 체크리스트에
         "딥링크 새로고침" 항목을 넣었고, 이후 프로젝트에선 배포 첫날 확인한다.
```

핵심은 **틀린 가설까지 말하는 것**이다. "처음엔 A 를 의심했는데 로그를 보니 B 였다" 가 있어야 추적 과정이 진짜가 되고, 꼬리 질문("왜 그 가설부터 봤나요?", "다른 방법은 없었나요?", "재발했나요?")에 답할 수 있다.

기억에 의존하면 6개월 뒤 면접 때 남는 건 "뭔가 404 났었는데…" 뿐이다. 프로젝트 중 막힐 때마다 저장소의 `docs/troubleshooting.md` 나 GitHub 이슈에 다음 네 칸을 그 자리에서 적는다.

| 칸 | 적을 것 |
| --- | --- |
| 증상 | 에러 메시지 원문, 재현 조건, 언제부터 |
| 추적 | 본 로그·쓴 도구·가설 순서(틀린 것 포함) |
| 해결 | 바꾼 것 한 줄 + 검증 방법 |
| 배운 것 | 일반화된 원칙 + 이후 바꾼 습관 |

면접용으로는 2~3개를 골라 둔다. 인프라·배포 하나, 코드 로직·데이터 하나, 협업(머지 충돌·소통) 하나면 균형이 좋다. 구글링이나 ChatGPT 로 답을 찾은 것도 괜찮다 — 다만 "왜 그 답이 맞았는지" 를 설명하지 못하면 감점이다.

## 헷갈리기 쉬운 것

- **성능 개선 경험**은 트러블슈팅의 특수한 형태로, "되던 것을 빠르게" 만든 것이라 전·후 수치가 필수다.
- **"가장 어려웠던 점" 질문**은 감정·과정·협업을 묻는 것이고, 트러블슈팅은 기술적 인과를 묻는 것. 후자의 답에는 로그·도구·설정 이름이 나와야 한다.
- **버그 수정 목록**은 이야기가 아니다. 열 개를 나열하기보다 하나를 네 단계로 깊게.
