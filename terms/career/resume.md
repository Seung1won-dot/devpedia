## 한 줄 정의

내가 **무엇을 어떻게 만들었고 결과가 뭔지**를 1~2장에 압축한 서류.

## 비유

영화 예고편. 2분 안에 볼 이유를 만들어야 하고, 본편(포트폴리오·면접)이 있다는 전제로 가장 좋은 장면만 고른다.

## 예시

```text
[나쁜 예]
Devpedia (2026.03 ~ 2026.06, 4인)
- React, Vite, TypeScript, Supabase, Docker, Caddy 사용
- 프론트엔드 개발 담당

[좋은 예 — 문제 · 역할 · 기술 · 성과]
Devpedia — IT 용어 사전 웹앱 (2026.03 ~ 06, 4인 중 프론트 1인)   github.com/…
- 문제 : 카드 300장 검색이 한글 입력 중 끊김(입력 1회당 300 ms)
- 역할 : 검색·카드 렌더링 담당, 빌드 시 terms.json 생성 스크립트 설계
- 기술 : React 18, Vite, TypeScript, Supabase(Postgres RLS), Caddy
- 성과 : 디바운스 + 사전 인덱스로 입력 지연 300 → 20 ms (Chrome Performance),
         Lighthouse 61 → 92, PR 리뷰 40건
```

나쁜 예의 문제는 셋이다. **기술 스택만 나열**해서 뭘 만들었는지 모르고, **팀 프로젝트에서 내 기여가 불명확**하고, **성과에 숫자가 없다**. 좋은 예는 한 줄 한 줄이 면접 질문의 씨앗이 된다 — 그래서 이력서에 쓴 모든 단어는 질문 대상이고, 안 써 본 기술은 빼는 게 안전하다.

두 번째 원칙은 **채용 공고의 키워드와 매핑**이다. 공고의 "자격 요건" 문장을 왼쪽에, 그에 대응하는 내 경험을 오른쪽에 놓고 빈칸이 있으면 그 공고는 아직 이르다.

| 공고 문장 | 이력서 문장 |
| --- | --- |
| RESTful API 설계 경험 | 카드 CRUD REST API 설계, OpenAPI 문서화 |
| RDBMS 사용 경험 | Postgres 스키마 설계, 인덱스로 목록 조회 48 → 1 ms |
| Git 기반 협업 | PR 기반 코드 리뷰, GitHub Actions CI 구성 |

체크리스트: 신입은 1~2장, PDF, 파일명 `이력서_이름_직무.pdf`. 상단에 이름·연락처·GitHub·블로그 링크(클릭되게). 프로젝트마다 문제·역할·기술·성과 4줄. 팀 프로젝트는 "N인 중 내 담당". 공고 키워드는 원문 표현 그대로. 수업 과제를 프로젝트로 부풀리지 않기. "열정", "빠르게 배웁니다" 같은 형용사 대신 숫자.

## 헷갈리기 쉬운 것

- **자기소개서**는 공채가 요구하는 문항형 글(지원 동기·성장 과정 등). 이력서는 사실·수치, 자소서는 서사. IT 서비스 기업·스타트업은 자소서 없이 이력서 + 포트폴리오만 받는 경우가 많다 [확인 필요].
- **포트폴리오**는 이력서의 한 줄을 화면·코드·다이어그램으로 증명하는 문서나 사이트. 이력서가 예고편이면 포트폴리오는 본편.
- **경력기술서**는 경력직이 회사별 업무를 적는 문서. 신입은 프로젝트 항목이 그 자리다.
