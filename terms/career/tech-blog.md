## 한 줄 정의

공부한 것과 **삽질하며 해결한 과정**을 글로 남기는 개발자의 공개 기록.

## 비유

등산 일지. 정상 사진(결과)보다 **"어디서 길을 잃었고 어떻게 찾았는지"** 를 적어 두면 다음 사람과 미래의 나에게 지도가 된다.

## 예시

```text
플랫폼          장점                                     단점
velog           개발자 전용, 마크다운, 가입 1분             꾸미기 자유도 낮음
tistory         국내 검색 노출 좋음, 오래 씀                에디터·코드 블록이 불편
GitHub Pages    저장소가 곧 블로그, 완전히 내 것             Jekyll/Hugo 초기 설정 품
Notion 공개     글쓰기가 제일 편함                          검색 노출 약함, 개발자 커뮤니티 없음
```

무엇을 쓰나.

```text
TIL          오늘 배운 것 3~5줄. 꾸준함 증명용 — 매일이 아니라 주 2~3회면 충분
삽질 기록    "Proxmox 에서 GPU 패스스루가 안 됨 → IOMMU 그룹 분리 문제 → 해결"
개념 정리    남에게 설명하듯 — Devpedia 카드 형식(정의·비유·예시·헷갈리는 것)이 그대로 글감
회고         프로젝트 끝나고 잘한 것·못한 것·다음엔 다르게 할 것
```

삽질 글의 뼈대는 정해져 있다 — 증상(에러 메시지 그대로 복사) → 환경(버전, OS) → 시도한 것과 왜 안 됐나 → 해결 → 원인 한 줄. 에러 메시지를 그대로 적어 두면 같은 문제로 검색한 사람이 찾아오고, 그게 곧 조회수이자 포트폴리오다. 면접관이 블로그에서 보는 것은 두 가지, 날짜 간격으로 드러나는 **꾸준함**과 글로 드러나는 **설명력**이다. 글을 또렷하게 쓰는 사람은 코드 리뷰 코멘트도, 장애 보고서도 또렷하게 쓴다고 보기 때문이다. 강의 내용을 베껴 쓴 글은 오히려 마이너스이고, 이력서에 링크를 걸 거면 가장 잘 쓴 글 3개를 상단에 고정한다. 면접에서는 "블로그에 쓴 그 문제, 지금 다시 만나면 어떻게 접근하겠어요?" 처럼 글이 질문의 출발점이 된다.

## 헷갈리기 쉬운 것

- **포트폴리오**는 결과물 정리, 블로그는 과정 기록. 프로젝트 페이지에서 관련 삽질 글로 링크를 건다.
- **README**는 그 프로젝트를 쓰는 사람을 위한 사용법. 블로그는 그 프로젝트를 만들다 겪은 일.
- **비공개 노션 메모**는 공부엔 좋지만 성실성의 증거가 되지 않는다. 공개가 핵심이다.
