## 한 줄 정의

내가 만든 프로젝트를 **어떤 문제를 어떻게 풀었는지** 보이게 정리한 모음.

## 비유

건축가의 작품집. 건물 사진(스크린샷)만 늘어놓는 게 아니라 **"이 땅은 좁고 경사져서 이렇게 설계했다"** 는 설명이 붙어야 실력이 보인다.

## 예시

프로젝트 하나당 이 체크리스트를 채운다. 못 채우는 항목이 많은 프로젝트는 빼는 게 낫다.

```text
[ ] 한 줄 소개 — 누구의 어떤 문제를 푸는가 ("연구실 신입이 IT 용어를 물어볼 곳이 없어서…")
[ ] 배포 링크 — 클릭하면 바로 돌아간다 (GitHub Pages·Vercel·홈서버 + Caddy)
[ ] GitHub 링크 — README 에 실행법, 커밋 이력에 과정이 살아 있음
[ ] 내 역할 — 팀 프로젝트면 "기여도 40%" 가 아니라 "검색·빌드 스크립트·PWA 를 내가"
[ ] 기술 선택 이유 — "React 씀" 이 아니라 "SEO 필요 없는 내부 툴이라 SPA + 정적 호스팅"
[ ] 문제 해결 1~2개 — 문제 → 원인 → 시도 → 결과, 숫자가 있으면 최고
[ ] 아쉬운 점·다음 계획 — 한계를 아는 사람이 신뢰받는다
```

Devpedia 를 예로 쓰면 이런 문장이 된다. "카드가 수백 장으로 늘자 매 요청마다 마크다운을 파싱하는 게 느려져, 빌드 때 `terms.json` 하나로 묶고 브라우저에서는 그 파일만 읽게 바꿨다. 대신 카드 형식이 깨지면 빌드가 실패하도록 검증 스크립트를 넣었다." 면접관이 포트폴리오를 보는 시간은 3분 안팎이고, 배포 링크가 있으면 "돌아가는 물건", 없으면 "코드 뭉치" 로 읽힌다. 개수는 깊이 있는 2~3개가 토이 프로젝트 8개보다 낫다 — 프로젝트마다 꼬리 질문 10개를 버틸 수 있어야 한다. 강의를 따라 만든 클론 코딩은 "내가 바꾼 점" 이 없으면 넣지 않는다. 면접에서는 "이 프로젝트에서 제일 잘한 결정 하나와 후회하는 결정 하나는?" 이 단골이다.

## 헷갈리기 쉬운 것

- **이력서**는 1~2장짜리 사실 요약. 포트폴리오는 이력서의 프로젝트 한 줄을 펼쳐 증명하는 자료다.
- **GitHub 프로필**은 저장소 모음일 뿐이다. 프로젝트별 설명과 정리가 없으면 포트폴리오가 아니다.
- **기술 블로그**는 과정의 기록, 포트폴리오는 결과물 중심. 서로 링크를 걸면 둘 다 살아난다.
