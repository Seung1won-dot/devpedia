## 한 줄 정의

장애가 끝난 뒤 **원인·타임라인·재발 방지책**을 사람 탓 없이 적어 남기는 문서.

## 비유

**비행기 사고 조사**. 조종사를 처벌하는 게 목적이 아니라 블랙박스를 읽고 "같은 사고가 다시 안 나게" 체크리스트와 절차를 고치는 것이다.

## 예시

```markdown
# 2026-09-28 RAG API 2시간 중단

- 영향: 14:10~16:05, 내부 사용자 12명의 질문 실패 (이달 SLO 버짓 55% 소진)
- 감지: 사용자 Slack 문의로 알게 됨 — 알림이 없었다는 것 자체가 문제
- 타임라인
  - 14:10 /data 디스크 100% → PostgreSQL 쓰기 실패
  - 15:40 "서버 느려요" 메시지 확인, SSH 접속
  - 16:05 오래된 학습 체크포인트 300GB 삭제 후 복구
- 근본 원인: 학습 스크립트가 체크포인트를 DB 와 같은 볼륨에 무제한 저장
- 잘 된 점: 원인 파악 후 복구까지 25분
- 액션 아이템
  - [ ] DiskAlmostFull 알림 추가 (담당 A, 10/05 까지)
  - [ ] 체크포인트 보관 개수 3개로 제한 (담당 B, 10/05 까지)
```

핵심은 **blameless** — "B 가 체크포인트를 안 지웠다"가 아니라 "지우지 않아도 되는 구조가 없었다"로 쓴다. 사람을 탓하는 순간 다음 장애는 숨겨진다. 액션 아이템은 담당자·기한이 있는 이슈로 등록해야 문서가 아니라 변화가 된다. 트레이드오프: 사소한 문제까지 전부 쓰면 아무도 안 쓰게 되니, 3인 연구실이면 "사용자 영향이 있었거나 SLO 버짓을 깎은 것"만 포스트모템을 쓰고 나머지는 이슈 한 줄로 끝내는 게 맞다.

## 헷갈리기 쉬운 것

- **회고(retrospective)** 는 스프린트마다 "일하는 방식"을 돌아보는 정기 행사, 포스트모템은 특정 장애 하나를 파는 비정기 문서.
- **장애 보고서(incident report)** 는 "무슨 일이 있었나"를 당일 위에 알리는 것, 포스트모템은 "왜, 그래서 뭘 바꿀 것인가"가 핵심이라 며칠 뒤에 나온다.
- **RCA(근본 원인 분석)** 는 포스트모템의 한 부분이다. 원인 하나로 끝내지 말고 "왜 감지가 늦었나", "왜 복구가 오래 걸렸나"까지 따진다.
